# T-004 — Track an authorized job as a private saved application

Status: proposed
Owner: unassigned
Branch/PR: —

## Why this matters

A saved private job is not yet an application record. Students need to return from saved applications to the same job and résumé work, and retain status, notes and a personal reminder after reload.

## Verified starting point

`src/app/(student)/saved/page.tsx` always renders `SavedApplicationsPreview`; its fictional cards mutate React state. There is no application API or shared Zod application contract. `saved_applications` already has an owner, job FK, unique `(user_id,job_id)`, status, `deadline`, notes and timestamps. Initial RLS restricts own records and authorizes jobs on INSERT, but UPDATE checks only the owner: direct clients could change a record's job reference without the original authorization check. Existing preview tests prove no database behavior. Deployment UNKNOWN.

## Plan and boundaries

- Product: add an explicit “Track application” action to an authorized job detail; repeat clicks return the existing own record. Link saved cards to `/jobs/[id]` and `/match/[id]`. Keep pasted-job save distinct from tracking an application.
- Data: add shared application schemas, a session-scoped adapter, authenticated create/list/update routes and migrations. Treat SQL `saved_applications.deadline` as the personal reminder date; never replace/verify `jobs.deadline`. Make owner/job immutable and recheck readable jobs for creation. Validate real dates, statuses, 4,000-character notes and stale edits at the write boundary. Inspect existing rows before applying constraints anywhere shared.
- Privacy: own RLS reads; inaccessible job content must be omitted while own tracking fields remain available. No request accepts an owner ID. Return indistinguishable missing/foreign errors. No fixtures in the production path.
- Verification: inspect UI/API/Zod/SQL/RLS/tests before editing, then run two fictional accounts against an isolated database and relevant fixture checks.

## Acceptance checks

- [ ] A tracks the same imported job twice and gets one own application; reload retains it.
- [ ] Status, personal reminder and notes save/reload atomically; stale edits conflict without loss.
- [ ] B and signed-out callers cannot read or mutate A's record; direct REST cannot retarget it to a foreign job.
- [ ] Authorized saved links return to the same job and own résumé version.
- [ ] Hidden/unavailable job content stays unavailable; own tracking data has a truthful fallback.
- [ ] Contract/demo docs and task include commands, actual results and deployment limits.

## Out of scope

Employer submissions, automatic applications, emails/notifications, résumé version pinning, calendar UI and external calendar sync. Preserve existing records; removal/archive is a separate explicit user action, not part of this save slice.
