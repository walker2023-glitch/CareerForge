# T-005 — Show private saved-application dates on the calendar

Status: proposed
Owner: unassigned
Branch/PR: —

## Why this matters

Calendar dates should come from the same private application records students edit, with a clear distinction between an employer deadline and their own reminder.

## Verified starting point

`src/app/(student)/calendar/page.tsx` imports `calendarFixtures` unconditionally and computes due states against `2026-11-13`. `src/lib/calendar/index.ts` already builds all-day events and Google/ICS exports from `CalendarApplication`. It assumes a non-null readable job. Fixtures include verification labels that do not establish real posting verification. Calendar tests cover sample behavior; there is no account-backed calendar loader/API. T-004 will supply the application contract and session-scoped source.

## Plan and boundaries

- Product: split the server loader from the interactive month view. Derive events from the caller's saved applications and readable job rows. Keep posting deadlines and personal reminders separate, including two events when both exist. Use the student's local date for due states; retain the fixed date only under an explicit fixture mode.
- Data/privacy: reuse T-004's loader and contracts rather than a separate calendar table. Recheck job access; an inaccessible listing must never leak title/company/description through cards, URLs or downloads. Show an own personal reminder generically or omit inaccessible job-derived events. Editing the reminder stays on the application record.
- Exports: exports happen only on user action and clearly disclose title/company/date being shared. Exclude notes and profile facts. Review ICS escaping (including bare carriage returns), date ranges, required metadata, stable UIDs and line folding; test parsing with an actual calendar parser. No Google account integration or background writes.
- Verification: inspect UI, any loader/API, Zod application/calendar mapping, migrations/RLS and tests; test account isolation and reminder-change/reload in an isolated database.

## Acceptance checks

- [ ] A's saved job deadline and personal reminder appear on their calendar after reload.
- [ ] Editing the reminder in saved applications changes the calendar without changing the posting deadline or verification state.
- [ ] B sees none of A's events; hidden job fields never appear in UI or exports.
- [ ] All-day dates stay on the intended date across time zones and DST; due states use the real local date.
- [ ] Google URLs and valid ICS contain only the disclosed event metadata and resist newline injection.
- [ ] Fixture calendar is explicitly labeled; no deployment/provider claims inferred from fixture tests.

## Out of scope

Background reminders, Google OAuth/two-way sync, email, automatic verification of deadlines, interview scheduling and a second event database.
